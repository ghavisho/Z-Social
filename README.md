> **وضعیت پروژه:** فاز ۱ تا ۱۵ کامل شده‌اند. فاز ۱۵ آخرین «آگاهانه ناتمام‌گذاشته‌شده»ی واقعی پروژه را حل کرد: عکس‌های پست/Moment/چت حالا هم از `next/image` استفاده می‌کنند (فشرده‌سازی خودکار WebP/AVIF، طبق بند ۴۹) — با یک مسیر پروکسی داخلی (`/api/media/[bucket]/[...path]`) که هر بار درخواست شود، یک Signed URL تازه می‌سازد و ریدایرکت می‌کند؛ چون آدرس خودِ پروکسی هیچ‌وقت تغییر نمی‌کند، کش next/image دیگر با انقضای امضا تداخل ندارد. این تغییر همچنین چند تولید Signed URL سمت سرور در Pulse را حذف کرد (کد ساده‌تر شد). نقشه راه باقی‌مانده در ادامه‌ی همین فایل — که رسماً فقط یک مورد باقی مانده.

> **فاز ۱۳:** فاز ۱۳ آخرین شکاف شناخته‌شده‌ی امنیتی را بست: **Rate Limit پیام‌های چت** — چون ارسال پیام مستقیماً از مرورگر به Supabase می‌رود (نه از یک مسیر API که بشود آن‌جا محدودش کرد)، این‌بار محدودیت را در خودِ دیتابیس، با یک Trigger روی جدول `messages`، اعمال کردیم (حداکثر ۳۰ پیام در دقیقه به‌ازای هر فرستنده) — سرعت Realtime حفظ می‌شود چون مسیر همان مسیر مستقیم قبلی‌ست. همچنین `loading.tsx`/`error.tsx`/`not-found.tsx` که طبق بند ۵۱ اسپک (هر صفحه: Loading/Empty/Error/Success) اصلاً وجود نداشتند، اضافه شدند.

## ۲. ساخت دیتابیس (Supabase)

Z از **Supabase** (PostgreSQL + Auth + Storage + Realtime) استفاده می‌کند — رایگان برای شروع.

1. در [supabase.com](https://supabase.com) ثبت‌نام کن.
2. یک پروژه جدید بساز (یک منطقه‌ی جغرافیایی نزدیک به کاربرانت انتخاب کن).
3. از داشبورد Supabase، بخش **SQL Editor** را باز کن.
4. فایل‌های زیر را **به همین ترتیب** اجرا کن:
   - `supabase/migrations/0001_init_schema.sql`
   - `supabase/migrations/0002_rls_policies.sql`
   - `supabase/migrations/0003_storage_and_cleanup.sql`
   - `supabase/migrations/0004_storage_read_fix.sql`
   - `supabase/migrations/0005_message_rate_limit.sql`
5. از بخش **Settings → API**، مقادیر زیر را کپی کن:
   - `Project URL`
   - `anon public key`
   - `service_role key` (این را فقط سمت سرور استفاده کن، هرگز منتشر نکن)

### فعال‌سازی پاک‌سازی خودکار (اختیاری ولی پیشنهادی)

برای پاک شدن خودکار ردیف‌های دیتابیس Momentهای منقضی، در Supabase Dashboard extension به نام `pg_cron` را فعال کن و سپس در SQL Editor اجرا کن:

```sql
select cron.schedule('y-cleanup-hourly', '0 * * * *', $$ select cleanup_expired_content(); $$);
```

این فقط ردیف دیتابیس را پاک می‌کند — برای پاک شدن خودِ فایل (عکس/ویدیوی Moment) از Storage هم، تابع Edge Function زیر را Deploy و زمان‌بندی کن (نیازمند [Supabase CLI](https://supabase.com/docs/guides/cli)):

```bash
supabase functions deploy cleanup-storage
```

سپس یک Cron خارجی (یا `pg_cron` + `pg_net`) هر ساعت این آدرس را صدا بزند:
```
https://YOUR-PROJECT.supabase.co/functions/v1/cleanup-storage
```
با هدر `x-cleanup-secret` برابر مقداری که در Environment Variable مربوط به آن Function (`CLEANUP_SECRET`) تنظیم کردی.

## ۳. تنظیم Environment Variables

فایل `.env.example` را کپی کن و نامش را به `.env.local` تغییر بده:

```bash
cp .env.example .env.local
```

سپس مقادیر واقعی Supabase و یک `SESSION_SECRET` تصادفی طولانی را داخلش قرار بده.

**هشدار:** فایل `.env.local` هرگز نباید داخل Git commit شود یا در ZIP نهایی قرار بگیرد — این فایل از قبل در `.gitignore` قرار دارد.

## ۷. انتشار روی اینترنت (Deploy)

### گزینه پیشنهادی: Vercel (سازگارترین با Next.js، Free Tier مناسب)

1. یک حساب در [vercel.com](https://vercel.com) بساز.
2. حساب GitHub خودت را به Vercel وصل کن.
3. پروژه‌ی Z را در یک Repository روی GitHub Upload/Push کن.
4. در Vercel، «Add New Project» را بزن و Repository را انتخاب کن.
5. **Build Command:** `npm run build` (به‌صورت پیش‌فرض تشخیص داده می‌شود)
6. **Output:** به‌صورت خودکار توسط Next.js مدیریت می‌شود.
7. در بخش Environment Variables پروژه در Vercel، همان مقادیر `.env.local` را وارد کن.
8. دکمه‌ی Deploy را بزن.

### جایگزین: Cloudflare Pages

اگر ترجیح می‌دهی از Cloudflare استفاده کنی، باید Next.js را با آداپتور `@cloudflare/next-on-pages` بیلد کنی. مراحل مشابه بالاست، با تفاوت در تنظیم Build Command طبق مستندات Cloudflare.

### Backend

نیازی به Deploy جداگانه برای Backend نیست — Supabase خودش میزبانی می‌شود.

## ۸. گرفتن URL عمومی

بعد از Deploy موفق، Vercel یک آدرس رایگان مثل:

```
y-project.vercel.app
```

به تو می‌دهد. این آدرس به‌صورت خودکار روی **HTTPS** است، پس PWA و همه‌ی قابلیت‌های امنیتی به‌درستی کار می‌کنند. هر کسی که این آدرس را داشته باشد می‌تواند:

- سایت را باز کند
- ثبت‌نام کند (Register)
- وارد شود (Login)
- از Z استفاده کند

## ۹. اتصال Domain اختصاصی

اگر یک دامنه (مثلاً `y-app.com`) خریداری کردی:

1. در تنظیمات پروژه در Vercel، بخش **Domains** را باز کن.
2. دامنه‌ات را وارد کن.
3. رکوردهای DNS که Vercel نشان می‌دهد (معمولاً یک رکورد `A` یا `CNAME`) را در پنل ثبت‌کننده‌ی دامنه‌ات اضافه کن.
4. صبر کن تا DNS منتشر شود (معمولاً چند دقیقه تا چند ساعت).

## ۱۴. ساخت نسخه‌ی قابل انتشار (dist)

از آن‌جا که Z یک اپلیکیشن Next.js با بخش‌های Server-side (API Routes، Middleware، Auth) است، خروجی آن یک سایت کاملاً Static نیست؛ نیاز به یک محیط اجرای Node (مثل Vercel) دارد. اگر در آینده نسخه‌ی کاملاً Static (بدون API Routes) لازم شد، می‌توان با `next export` یک پوشه‌ی `dist/`/`out/` گرفت — اما در آن حالت، مسیرهای API باید به یک Backend جدا (مثلاً Supabase Edge Functions) منتقل شوند.

## ۱۶. نقشه راه (چه چیزی هنوز کامل نیست)

فاز ۱ تا ۱۵ کامل شده‌اند. با رفع next/image و تکمیل Loading skeletonها، عملاً هرچیزی که در توان یک محیط بدون اجرای واقعی بود، انجام شد. یک مورد واقعی باقی مانده — و این یکی را هیچ مقدار کدنویسی بیشتر هم حل نمی‌کند:

- **TURN Server اختصاصی برای تماس صوتی.** یک TURN رایگان و عمومی (openrelay.metered.ca) از قبل به‌عنوان fallback تنظیم شده، پس تماس صوتی روی اکثر شبکه‌ها کار می‌کند. اما TURN عمومی، مشترک بین همه‌ی اینترنت است و نرخ محدودی دارد؛ برای قابلیت‌اطمینان در مقیاس واقعی، باید یک سرویس TURN اختصاصی (مثل Twilio یا Xirsys) بخری و مقادیرش را در `NEXT_PUBLIC_TURN_URL`/`_USERNAME`/`_CREDENTIAL` بگذاری. این یک تصمیم هزینه‌ای/عملیاتی است، نه چیزی که با کد حل شود.

**از این‌جا به بعد، تنها راه واقعی برای رسیدن به قطعیت، اجرای واقعیه.** `TESTING_CHECKLIST.md` را وقتی به سیستم دسترسی داشتی، ردیف‌به‌ردیف تیک بزن؛ من همین‌جا برای رفع هر خطایی که پیدا کنی آماده‌ام — و با توجه به این‌که این پروژه بارها فقط با مرور دقیق کد (نه اجرا) باگ‌های واقعی داشته، تست دستی واقعی احتمالاً چیزهای بیشتری پیدا می‌کند.

## ۱۷. به‌روزرسانی از پنل ادمین (آپلود ZIP، مخصوص Netlify)

بعد از راه‌اندازی اولیه (که همچنان طبق بخش‌های بالا نیاز است)، برای هر به‌روزرسانی‌ی بعدی می‌توانی به‌جای بازکردن GitHub و درگ‌ودراپ‌کردن فایل‌ها، مستقیماً از داخل خودِ Z یک فایل ZIP جدید آپلود کنی. این قابلیت فایل‌ها را مستقیم به مخزن GitHub‌ات می‌فرستد (دقیقاً همان کاری که خودت دستی انجام می‌دادی)، و چون Netlify از قبل به آن مخزن وصل است، خودش خودکار Build و منتشرش می‌کند — یعنی این قابلیت مستقیماً با Netlify صحبت نمی‌کند، فقط با GitHub، و Netlify (یا هر سرویس دیگری که به همان مخزن وصل باشد) خودش بقیه‌ی کار را انجام می‌دهد.

**دیتابیس (کاربران، پست‌ها، پیام‌ها) کاملاً جدا از این فرآیند است** — چون Netlify (جایی که کد اجرا می‌شود) و Supabase (جایی که داده ذخیره می‌شود) دو سیستم کاملاً مستقل‌اند؛ آپلود کد جدید هرگز داده‌ای را پاک نمی‌کند یا لمس نمی‌کند.

### تنظیم یک‌بار (قبل از اولین استفاده)

سه مقدار لازم داری — همه از GitHub:

1. **GITHUB_TOKEN:**
   - وارد [github.com/settings/tokens?type=beta](https://github.com/settings/tokens?type=beta) شو (Fine-grained tokens).
   - **Generate new token** بزن.
   - یک اسم بده (مثلاً `z-admin-deploy`)، **Repository access** را روی **Only select repositories** بگذار و مخزن `z-social` را انتخاب کن.
   - در بخش **Permissions** → **Repository permissions**، مقابل **Contents** گزینه‌ی **Read and write** را انتخاب کن (این تنها دسترسی‌ای‌ست که لازم است).
   - **Generate token** بزن، مقدار نمایش‌داده‌شده را کپی کن (فقط یک‌بار نشان داده می‌شود).

2. **GITHUB_OWNER:** یوزرنیم GitHub خودت (همانی که در آدرس `github.com/یوزرنیم/z-social` می‌آید).

3. **GITHUB_REPO:** اسم مخزن — اگر همان چیزی که در بخش ۴ ساختی است، معمولاً `z-social`.

این سه مقدار (به‌علاوه `GITHUB_BRANCH=main` که از قبل پیش‌فرض است) را در **Netlify → Site configuration → Environment variables** اضافه کن — دقیقاً مثل سه مقدار Supabase — و یک‌بار **Trigger deploy** بزن تا اعمال شوند.

**اختیاری — برای دیدن وضعیت زنده‌ی Build داخل پنل ادمین** (وگرنه فقط می‌گوید «فرستاده شد، داشبورد Netlify را چک کن»، که کاملاً کافی هم هست):
- **NETLIFY_TOKEN:** از **User settings → Applications → Personal access tokens** در Netlify بساز.
- **NETLIFY_SITE_ID:** از **Site configuration → General → Site details → Site information → API ID**.

1. فایل ZIP جدیدی که از من (Claude) دریافت می‌کنی را دانلود کن — **بدون Extract کردن**.

5. صبر کن (۱ تا ۳ دقیقه) تا وضعیت به ✅ برسد، یا لینک Commit را برای چک‌کردن دستی در GitHub/Netlify بزن.

### چیزهایی که این روش **نمی‌کند** (مهم است بدانی)

- **تغییرات دیتابیس را خودکار اعمال نمی‌کند.** اگر یک به‌روزرسانی شامل فایل migration جدید در `supabase/migrations/` باشد (مثلاً `0008_xxx.sql`)، باز هم باید طبق بخش ۲ همین README، آن فایل SQL را دستی در Supabase SQL Editor اجرا کنی. من هربار که چنین فایلی اضافه کنم، صریحاً بهت می‌گویم.
- محدودیت حجم: فایل ZIP نباید بیشتر از ۵۰ مگابایت باشد (پروژه‌ی Z معمولاً چند صد کیلوبایت است، جای نگرانی نیست).
- این قابلیت هر بار **کل مخزن را با محتوای همان ZIP جایگزین می‌کند** (نه اضافه‌کردن) — چون همیشه فایل کامل پروژه را می‌فرستم، این دقیقاً همان چیزی‌ست که باید اتفاق بیفتد؛ اگر یک‌بار فقط چندتا فایل جزئی آپلود کنی، بقیه‌ی فایل‌های مخزن حذف می‌شوند. همیشه کل ZIP پروژه را آپلود کن، نه یک زیرمجموعه.
- این قابلیت فقط برای **مدیر اصلی (super_admin)** در دسترس است — نه ادمین‌های معمولی — چون قدرت انتشار کد دلخواه روی سایتت را می‌دهد.

## ۱۸. تست خودکار Build با GitHub Actions (بدون نیاز به Node.js روی کامپیوترت)

یک فایل در مسیر `.github/workflows/ci.yml` در پروژه هست که کاری شبیه یک «Build واقعی» را جای تو انجام می‌دهد — روی سرورهای گیت‌هاب، نه روی کامپیوترت:

1. پروژه را (طبق بخش ۱۳) در یک Repository روی GitHub Push کن.
2. به تب **Actions** در صفحه‌ی Repository برو.
3. یک Workflow به اسم «Z — CI» می‌بینی که خودکار اجرا شده.
4. ✅ سبز یعنی `npm install`، تست‌ها، و `npm run build` بدون خطا رد شدند — یعنی می‌توانی با خیال راحت روی Vercel هم Deploy کنی.
5. ❌ قرمز یعنی جایی خطا داده — روی آن کلیک کن، پیام خطای دقیق را می‌بینی؛ همان پیام را برایم بفرست تا رفعش کنم.

این یعنی حتی بدون این‌که Node.js را روی کامپیوتر خودت نصب کنی، فقط با Push کردن می‌توانی بفهمی پروژه واقعاً کار می‌کند یا نه.

## معماری کوتاه

- **Frontend:** Next.js 14 (App Router) + TypeScript + Tailwind
- **Backend:** Next.js API Routes + Supabase (Postgres, Auth, Storage, Realtime)
- **Auth:** نام‌کاربری/رمزعبور (از طریق ایمیل داخلی `username@y.local` روی Supabase Auth)
- **PWA:** `manifest.json` + `sw.js` (stale-while-revalidate برای assetهای static، بدون کش کردن ترافیک Supabase)

هر سؤالی درباره‌ی بخش خاصی از پروژه داشتی، در فایل‌های مربوطه کامنت‌های توضیحی فارسی/انگلیسی گذاشته شده — یا مستقیم بپرس.
